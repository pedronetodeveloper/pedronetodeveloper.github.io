Fundação em Java: o essencial pra se virar no backend

Pedro Neto • 14 jul 2026 • 15 min de leitura

Por que você deveria entender isso?

Quando entrei no backend, abri meu primeiro projeto Spring e me deparei com um monte de palavras que só tinha visto na faculdade, porém não tinha profundidade de entendimento ainda: entidade, DTO, record, stream.

Mas no final a real é: qualquer codebase Java de backend que você abrir vai ter esses conceitos em todo lugar. Não dá pra fugir e você precisa saber my friend.

Levei mais tempo do que gostaria de admitir pra conectar esses pontos. Espero que este post encurte esse caminho pra você.

🧱 O básico que a gente esquece (e não devia)

Variável guarda valor, loop repete trabalho, try/catch trata o que pode dar errado. Parece óbvio — até o code review mostrar que não é.

Antes de entidade e stream, um passeio rápido pelo alicerce do alicerce. Se você domina isso, pula pra próxima seção sem culpa.

Variáveis: primitivos e referências

int idade = 25;              // primitivo: guarda o VALOR direto
double altura = 1.75;
boolean ativo = true;

String nome = "Pedro";       // referência: aponta pra um OBJETO
Integer pontos = null;       // objeto pode ser null; primitivo nunca

var cidade = "Recife";       // o compilador infere o tipo (Java 10+)
final double TAXA = 0.05;    // final = não muda nunca mais
  • Primitivo (int, double, boolean) guarda o valor e nunca é null. Referência (String, Integer, seus objetos) aponta pro objeto — e pode ser null, então trate.
  • var só funciona em variável local e não muda o tipo depois — é inferência, não mágica.
  • final em constantes e no que não deve ser reatribuído. Quanto mais final, menos surpresa.

for, while e for-each: qual repete o quê

// for clássico: você SABE quantas vezes vai rodar
for (int i = 0; i < 3; i++) {
    System.out.println("tentativa " + i);
}

// for-each: percorrer coleção (seu caso em 90% do tempo)
for (String tech : List.of("Java", "Spring", "AWS")) {
    System.out.println(tech);
}

// while: repete ENQUANTO a condição vale (não sabe quantas vezes)
while (fila.temPendencia()) {
    fila.processarProxima();
}

// do-while: igual ao while, mas roda PELO MENOS uma vez
do {
    resposta = perguntarAoUsuario();
} while (!resposta.valida());

Regra de bolso: quantidade conhecida → for; coleção → for-each; condição → while; "executa e depois verifica" → do-while. E guarda essa: mais pra frente, o for-each em coleção vai virar stream.

try/catch: quando usar (e quando não)

// BOM: erro esperado, e você TEM o que fazer com ele
try {
    int quantidade = Integer.parseInt(entradaDoUsuario);
} catch (NumberFormatException e) {
    System.out.println("Digite um número válido");
}

// MELHOR AINDA: try-with-resources fecha o recurso sozinho
try (var leitor = Files.newBufferedReader(caminho)) {
    return leitor.readLine();
}
  • Capture só o que você consegue tratar. Não tem o que fazer com o erro ali? Deixa ele subir pra quem tem (no Spring, um handler global resolve).
  • Try-with-resources sempre que abrir arquivo, conexão ou stream — fecha sozinho até quando dá erro.
  • Exceção não é fluxo de controle. Validar com if é de graça; lançar exceção é caro e esconde a intenção.
O clássico que assombra: catch (Exception e) { } — o catch vazio, engolidor de erro. A aplicação quebra em silêncio e você caça o bug por horas onde ele não está. Se capturou, faça algo: logue, avise, relance. Silêncio nunca.

🪞 Entidade: o espelho do banco de dados

Entidade é a classe que representa uma tabela do banco dentro do seu código.

Cada linha da tabela vira um objeto. Cada coluna vira um atributo. No mundo Spring, você marca isso com anotações do JPA:

Produto.java

import jakarta.persistence.*;
import java.math.BigDecimal;

@Entity
@Table(name = "produtos")
public class Produto {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String nome;
    private BigDecimal preco;
    private boolean ativo;

    // JPA exige um construtor vazio
    public Produto() {}

    public Produto(String nome, BigDecimal preco, boolean ativo) {
        this.nome = nome;
        this.preco = preco;
        this.ativo = ativo;
    }

    // getters e setters...
    public Long getId() { return id; }
    public String getNome() { return nome; }
    public BigDecimal getPreco() { return preco; }
    public boolean isAtivo() { return ativo; }
}

Repare em dois detalhes que confundem todo jr:

  • @GeneratedValue — o banco gera o ID pra você. Você nunca seta o ID na mão.
  • Preço é BigDecimal, não double — double tem erro de arredondamento e dinheiro não perdoa. Isso já derrubou boleto em produção por aí.
Quando usar: pra representar as tabelas do banco dentro da aplicação — e só. Entidade não sai pelo controller nem vira contrato de API: ela fica no domínio, quem viaja é o DTO. Se a entidade está aparecendo no JSON da resposta, algo furou.

📦 DTO: o que entra e sai da sua API

DTO (Data Transfer Object) é a classe que carrega dados entre a sua API e o mundo externo — sem expor a entidade.

"Mas por que não devolver a entidade direto no controller?" Eu fiz essa pergunta. E fiz o erro também. Três motivos pra não fazer:

  1. Segurança: a entidade pode ter campos que não devem vazar (senha, custo interno, flags de negócio).
  2. Acoplamento: se o front depende do formato da entidade, qualquer mudança no banco quebra o contrato da API.
  3. Lazy loading: entidade com relacionamento preguiçoso serializando fora da transação = LazyInitializationException na sua cara.

Um DTO clássico é simples assim:

ProdutoDTO.java

public class ProdutoDTO {

    private final String nome;
    private final BigDecimal preco;

    public ProdutoDTO(String nome, BigDecimal preco) {
        this.nome = nome;
        this.preco = preco;
    }

    public String getNome() { return nome; }
    public BigDecimal getPreco() { return preco; }

    // Converte entidade -> DTO num lugar só
    public static ProdutoDTO from(Produto p) {
        return new ProdutoDTO(p.getNome(), p.getPreco());
    }
}

Muito boilerplate pra pouca coisa, né? Concordo. É exatamente por isso que existem records.

✨ Records: o DTO que o Java escreve pra você

Record é uma classe imutável onde o Java gera construtor, getters, equals, hashCode e toString automaticamente.

Aquele DTO inteiro de cima vira uma linha (Java 16+):

ProdutoResponse.java

public record ProdutoResponse(String nome, BigDecimal preco) {

    public static ProdutoResponse from(Produto p) {
        return new ProdutoResponse(p.getNome(), p.getPreco());
    }
}

O acesso muda de getNome() pra nome(), e pronto. E dá pra validar na entrada com o construtor compacto:

CriarProdutoRequest.java

public record CriarProdutoRequest(String nome, BigDecimal preco) {

    public CriarProdutoRequest {
        if (preco == null || preco.signum() < 0) {
            throw new IllegalArgumentException("Preço não pode ser negativo");
        }
    }
}
Quando usar: record pra DTO, request, response e retorno de query — tudo que carrega dado pra fora. NÃO use pra entidade JPA (ela precisa de construtor vazio e de mudar de estado, e record é imutável) nem pra objeto que muda ao longo da vida. Regra prática: request e response? Record. Entidade? Classe normal.

🔄 Cast: do simples ao sofisticado

Cast é dizer pro compilador: "confia, esse valor é desse tipo aqui".

O simples: tipos primitivos

Quando não perde informação, o Java converte sozinho (widening). Quando pode perder, ele te obriga a assumir o risco (narrowing):

int inteiro = 42;
long largo = inteiro;      // implícito: int cabe em long
double preciso = inteiro;  // implícito: int cabe em double

double pi = 3.99;
int truncado = (int) pi;   // explícito: vira 3 (trunca, NÃO arredonda!)

Integer caixa = 42;        // autoboxing: int -> Integer
int semCaixa = caixa;      // unboxing: Integer -> int
Pegadinha do unboxing: se caixa for null, o unboxing lança NullPointerException. Campo Integer vindo do banco pode ser null — cuidado ao jogar direto num int.

O sofisticado: cast de objetos

Downcast (de tipo genérico pra tipo específico) só funciona se o objeto realmente for daquele tipo. Por isso sempre vem com instanceof:

Object obj = buscarQualquerCoisa();

// Jeito clássico (qualquer versão do Java)
if (obj instanceof String) {
    String s = (String) obj;
    System.out.println(s.toUpperCase());
}

// Pattern matching (Java 16+): testa E declara numa tacada só
if (obj instanceof String s) {
    System.out.println(s.toUpperCase());
}

E no Java 21 dá pra ir além com switch por tipo:

String descricao = switch (obj) {
    case String s     -> "Texto: " + s;
    case Integer i    -> "Número: " + i;
    case Produto p    -> "Produto: " + p.getNome();
    default           -> "Não sei o que é isso";
};
Erro comum: cast sem verificar o tipo. (String) num onde num é um Integer compila normal e explode em runtime com ClassCastException. O compilador confiou em você — não decepcione ele.
Quando usar: cast explícito só quando não tem jeito — API antiga, Object genérico, integração legada. Se você está fazendo cast toda hora no seu próprio código, o recado é outro: provavelmente falta um generic ou um polimorfismo no design.

🗂️ Collections: List, Set e Map

Collections são as estruturas que guardam vários objetos. A escolha certa depende de uma pergunta: como você vai buscar o dado depois?
InterfaceServe paraImplementação padrão
ListOrdem importa, duplicata pode. É a lista "normal".ArrayList
SetSem duplicata. Verificar "já existe?" é instantâneo.HashSet
MapBuscar valor por chave (tipo um dicionário).HashMap
 
List<String> techs = new ArrayList<>(List.of("Java", "Spring", "AWS", "Java"));
System.out.println(techs.size());        // 4 — List aceita duplicata

Set<String> unicas = new HashSet<>(techs);
System.out.println(unicas.size());       // 3 — Set removeu o "Java" repetido

Map<String, Integer> horasEstudo = new HashMap<>();
horasEstudo.put("Java", 120);
horasEstudo.put("Spring", 80);
System.out.println(horasEstudo.get("Java")); // 120 — busca direta pela chave
Se você está com pressa: 90% do tempo é ArrayList, HashSet e HashMap. Declare sempre pelo tipo da interface (List, Set, Map) — trocar a implementação depois fica indolor.

Detalhe que me pegou: List.of(...) cria lista imutável. Se tentar dar add() nela, toma UnsupportedOperationException. Quer mexer depois? Embrulha num new ArrayList<>(...) como no exemplo.

Quando usar: ordem e duplicata? List. Garantir que não repete? Set. Buscar por chave? Map. E o teste definitivo: se você se pegou escrevendo if (!lista.contains(x)) antes de adicionar, você queria um Set desde o começo.

🌊 Streams: transformar dados sem for

Stream é uma esteira de transformação: os dados entram de um lado, passam por filtros e transformações, e saem prontos do outro.

O trio que resolve quase tudo: filter (peneira), map (transforma), collect (junta o resultado). Olha um caso real de backend — pegar produtos ativos e converter pra DTO:

List<Produto> produtos = produtoRepository.findAll();

// Sem stream: umas 6 linhas de for + if + add
// Com stream:
List<ProdutoResponse> ativos = produtos.stream()
    .filter(Produto::isAtivo)            // peneira: só os ativos
    .map(ProdutoResponse::from)          // transforma: entidade -> DTO
    .toList();                           // junta numa List (Java 16+)

Somar valores? reduce:

BigDecimal total = produtos.stream()
    .filter(Produto::isAtivo)
    .map(Produto::getPreco)
    .reduce(BigDecimal.ZERO, BigDecimal::add);

Agrupar? Collectors:

import java.util.stream.Collectors;

// Separa em dois grupos: ativos (true) e inativos (false)
Map<Boolean, List<Produto>> porStatus = produtos.stream()
    .collect(Collectors.partitioningBy(Produto::isAtivo));
Erro que EU cometi: reusar um stream. Stream é descartável — depois de uma operação final (collect, count, forEach), ele morre. Usar de novo lança IllegalStateException: stream has already been operated upon or closed. Precisa de novo? Chama .stream() de novo na collection.
Quando usar: stream pra transformar, filtrar e agregar coleções. NÃO force stream onde um for simples é mais legível — uma linha gigante com 8 operações encadeadas é pior que um loop claro. Legibilidade ganha do estilo.

⚠️ O erro comum que junta tudo

O clássico dos clássicos: devolver a entidade direto no controller. Funciona no teste local, passa no code review desatento, e aí um dia alguém adiciona um relacionamento na entidade e sua API começa a vazar dado ou estourar LazyInitializationException.

O fluxo saudável, juntando tudo que vimos:

@GetMapping("/produtos")
public List<ProdutoResponse> listarAtivos() {
    return produtoRepository.findAll().stream()  // entidades do banco
        .filter(Produto::isAtivo)                // stream: peneira
        .map(ProdutoResponse::from)              // record: converte
        .toList();                               // collection: entrega
}

Entidade fica no domínio, record sai pela API, stream faz a ponte. É esse padrão que você vai ver (e escrever) todo santo dia.

A história por trás desse post

Tudo que você leu aqui foi o que me carregou na prática. Comecei como estagiário na TIVIT, uma consultoria onde fazia projetos pra clientes e internos — e em pouco mais de 2 anos saí de estagiário pra fullstack pleno.

Nessa trajetória, o que separou minha evolução de estagiário a jr foi o básico bem dominado. Variável, loop, exceção, entidade, record, stream — é isso que aparece em TODO code review, em TODA sprint, em qualquer stack. Domina o alicerce que o resto vem.

Conclusão

Se você sair daqui com uma frase, que seja essa: entidade espelha o banco, record carrega os dados pra fora, e stream faz a transformação no meio. Dominou esse fluxo, você se vira em qualquer backend Java.
