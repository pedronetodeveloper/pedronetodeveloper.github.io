Spring MVC vs Hexagonal:
a evolução de um dev backend

Pedro Neto • 14 jul 2026 • 15 min de leitura

Eu comecei a carreira acoplando o máximo do Spring no meu código — e era ótimo. Hoje trabalho num banco onde o hexagonal é pregado e a regra é desacoplar de framework sempre que dá. Esse post é essa jornada: duas mentalidades, o mesmo caso de uso, dois códigos completamente diferentes.

primeiro emprego → Spring MVC → banco → Hexagonal
a mentalidade "Spring me poupa um tempo tremendo não preciso me preocupar, Meu trabalho e entregar feature."

Todo mundo começa aqui — e muita empresa boa roda a vida inteira assim, faturando. No Spring MVC clássico, você abraça o ecossistema: anotação em tudo, convenção sobre configuração, e o framework costurando as camadas por baixo dos panos. O foco é produtividade — você sai do zero pra uma API funcionando em uma tarde, e isso é entregar valor de verdade.

A arquitetura é a famosa três camadas, e o Spring está presente em todas elas:

Request HTTP │ ▼ @RestController ──▶ @Service ──▶ JpaRepository (recebe/valida) (regra de (fala com o negócio) banco) ▲ │ └── Spring em TODAS as camadas ◀───┘

O código: o framework trabalhando pra você

Vamos pro caso de uso que todo dev já fez: cadastrar um produto. Repara como cada classe usa o framework a seu favor — até o DTO valida com Bean Validation, sem você escrever um if:

Produto.java — a entidade É a tabela (e às vezes vira o modelo de tudo)

@Entity
@Table(name = "produtos")
public class Produto {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String nome;

    @Column(nullable = false)
    private BigDecimal preco;

    private boolean ativo;

    // construtor vazio exigido pelo JPA, getters e setters...
}

CriarProdutoRequest.java — DTO com validação do framework

public record CriarProdutoRequest(

    @NotBlank(message = "Nome é obrigatório")
    String nome,

    @NotNull @Positive(message = "Preço deve ser positivo")
    BigDecimal preco
) {}

ProdutoService.java — regra de negócio gerenciada pelo Spring

@Service
public class ProdutoService {

    private final ProdutoRepository repository;

    public ProdutoService(ProdutoRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public Produto criar(CriarProdutoRequest request) {
        if (repository.existsByNome(request.nome())) {
            throw new ProdutoJaExisteException(request.nome());
        }
        Produto produto = new Produto(request.nome(), request.preco(), true);
        return repository.save(produto);
    }
}

ProdutoController.java — a porta de entrada, 100% Spring

@RestController
@RequestMapping("/produtos")
public class ProdutoController {

    private final ProdutoService service;

    public ProdutoController(ProdutoService service) {
        this.service = service;
    }

    @PostMapping
    public ResponseEntity<ProdutoResponse> criar(
            @RequestBody @Valid CriarProdutoRequest request) {
        Produto produto = service.criar(request);
        return ResponseEntity
            .status(HttpStatus.CREATED)
            .body(ProdutoResponse.from(produto));
    }
}

ProdutoRepository.java — o Spring Data escreve o SQL pra você

public interface ProdutoRepository extends JpaRepository<Produto, Long> {
    boolean existsByNome(String nome);
}

Cinco arquivos, quase nada de código "meu", e a API está no ar com validação, transação e persistência. É por isso que o Spring dominou o mercado: o custo de entrar é baixíssimo e a entrega é imediata. Com esse setup, um jr se vira sozinho e coloca feature em produção na primeira semana.

Vantagens e pontos de atenção

Nada aqui é "errado". São escolhas — e toda escolha tem um custo que aparece dependendo do tamanho e da vida útil do sistema:

✅ Vantagens

  • Velocidade brutal: CRUD completo em horas, não dias.
  • Menos código: o framework gera SQL, valida, serializa, gerencia transação.
  • Convenção: qualquer dev Spring abre o projeto e se acha em minutos.
  • Ecossistema: security, cache, mensageria — tudo plugável com uma anotação.

⚠️ Pode ficar perigoso quando...

  • A regra de negócio cresce: ela fica entrelaçada com o Spring, e separar depois custa caro.
  • O sistema precisa de muitos testes: testar service pede contexto Spring ou mocks, e o build vai ficando lento.
  • O domínio vira só getters/setters: a regra se espalha pelos services e ninguém sabe mais onde ela mora.
  • Chega uma migração grande: trocar framework ou subir versão major mexe em tudo ao mesmo tempo.
O erro que eu cometi nessa fase: deixar a entidade JPA circular pela aplicação inteira — controller, service, até no front via JSON. Quando precisei mudar uma coluna do banco, quebrei o contrato da API sem perceber. Entidade é detalhe de persistência, não moeda de troca.
Quando usar: MVPs, provas de conceito, CRUDs internos, times pequenos com prazo apertado, e sinceramente — a maioria dos sistemas que nunca vão ter regra de negócio complexa. Produtividade é um argumento de arquitetura válido. Começando com MVC você se vira, entrega valor e aprende o ecossistema. O perigo não é o MVC em si — é usar ele num sistema que já nasceu pedindo outra coisa.
a mentalidade "O framework é um detalhe. Minha regra de negócio tem que sobreviver à troca de banco, de framework e de moda. O domínio é o centro; o resto é plugin."

Aí você entra num banco — no meu caso, literalmente um banco — e descobre que sistema financeiro vive 15, 20 anos. Framework muda, banco de dados muda, até a empresa muda de cloud. O que não pode mudar quebrando tudo? A regra de negócio.

A Arquitetura Hexagonal (ou Ports & Adapters) inverte a lógica do MVC: em vez do framework abraçar seu código, seu código define contratos (ports) e o framework se encaixa neles (adapters). O núcleo — domínio e casos de uso — é Java puro. Zero anotação. Zero import de Spring.

ADAPTADORES DE ENTRADA NÚCLEO (Java puro) ADAPTADORES DE SAÍDA ┌─────────────────────┐ ┌──────────────────────────┐ ┌──────────────────────┐ │ @RestController │ │ CriarProdutoUseCase │ │ @Repository (JPA) │ │ Consumer Kafka │ ──▶ │ Produto (domínio) │ ──▶ │ Client HTTP │ │ Job agendado │ │ ProdutoRepositoryPort │ │ Fila / Cache │ └─────────────────────┘ │ (interface = contrato) │ └──────────────────────┘ Spring mora aqui └──────────────────────────┘ Spring mora aqui Spring NÃO entra aqui

O código: o domínio não conhece o Spring

Mesmo caso de uso — cadastrar produto. Mas agora repara: as três primeiras classes não têm UM import de framework. Compilam sem Spring no classpath.

domain/Produto.java — modelo rico, se valida sozinho, Java puro

public class Produto {

    private final Long id;
    private final String nome;
    private final BigDecimal preco;
    private boolean ativo;

    public Produto(Long id, String nome, BigDecimal preco, boolean ativo) {
        if (nome == null || nome.isBlank()) {
            throw new DominioException("Nome é obrigatório");
        }
        if (preco == null || preco.signum() <= 0) {
            throw new DominioException("Preço deve ser positivo");
        }
        this.id = id;
        this.nome = nome;
        this.preco = preco;
        this.ativo = ativo;
    }

    public void desativar() {          // comportamento mora NO domínio,
        this.ativo = false;            // não num service genérico
    }

    // getters...
}

application/port/ProdutoRepositoryPort.java — o contrato (port de saída)

public interface ProdutoRepositoryPort {

    boolean existePorNome(String nome);

    Produto salvar(Produto produto);
}

application/CriarProdutoUseCase.java — o caso de uso, Java puro

public class CriarProdutoUseCase {

    private final ProdutoRepositoryPort repository;

    public CriarProdutoUseCase(ProdutoRepositoryPort repository) {
        this.repository = repository;
    }

    public Produto executar(String nome, BigDecimal preco) {
        if (repository.existePorNome(nome)) {
            throw new ProdutoJaExisteException(nome);
        }
        Produto produto = new Produto(null, nome, preco, true);
        return repository.salvar(produto);
    }
}

Percebeu a mágica? O caso de uso depende da interface ProdutoRepositoryPort, não do JPA. Ele não sabe (nem quer saber) se o dado vai pro Postgres, pro Mongo ou pra um HashMap num teste. Agora sim, o Spring entra — só na borda, como detalhe de infraestrutura:

infrastructure/persistence/ProdutoRepositoryAdapter.java — adapter de saída

@Component
public class ProdutoRepositoryAdapter implements ProdutoRepositoryPort {

    private final ProdutoJpaRepository jpaRepository;

    public ProdutoRepositoryAdapter(ProdutoJpaRepository jpaRepository) {
        this.jpaRepository = jpaRepository;
    }

    @Override
    public boolean existePorNome(String nome) {
        return jpaRepository.existsByNome(nome);
    }

    @Override
    public Produto salvar(Produto produto) {
        ProdutoEntity entity = ProdutoEntity.from(produto); // domínio -> entidade JPA
        return jpaRepository.save(entity).toDomain();       // entidade -> domínio
    }
}

infrastructure/web/ProdutoController.java — adapter de entrada

@RestController
@RequestMapping("/produtos")
public class ProdutoController {

    private final CriarProdutoUseCase criarProduto;

    public ProdutoController(CriarProdutoUseCase criarProduto) {
        this.criarProduto = criarProduto;
    }

    @PostMapping
    public ResponseEntity<ProdutoResponse> criar(@RequestBody CriarProdutoRequest request) {
        Produto produto = criarProduto.executar(request.nome(), request.preco());
        return ResponseEntity
            .status(HttpStatus.CREATED)
            .body(ProdutoResponse.from(produto));
    }
}

infrastructure/config/UseCaseConfig.java — o Spring monta o quebra-cabeça

@Configuration
public class UseCaseConfig {

    @Bean
    public CriarProdutoUseCase criarProdutoUseCase(ProdutoRepositoryPort repository) {
        return new CriarProdutoUseCase(repository);  // new na mão: o use case
    }                                                // nem sabe que virou bean
}

Nota o detalhe: existe uma ProdutoEntity (JPA, na infraestrutura) separada do Produto (domínio). Sim, é mapeamento a mais. É o preço do desacoplamento — e em sistema grande, ele se paga.

E o teste? É aqui que o hexagonal brilha

class CriarProdutoUseCaseTest {

    @Test
    void naoDeveCriarProdutoDuplicado() {
        // fake em memória: nenhum Spring, nenhum mock framework, nenhum banco
        ProdutoRepositoryPort fake = new ProdutoRepositoryFake(
            new Produto(1L, "Teclado", new BigDecimal("199.90"), true)
        );
        CriarProdutoUseCase useCase = new CriarProdutoUseCase(fake);

        assertThrows(ProdutoJaExisteException.class,
            () -> useCase.executar("Teclado", new BigDecimal("99.90")));
    }
}

Esse teste roda em milissegundos, sem subir contexto, sem @SpringBootTest, sem Testcontainers. Num sistema com 3 mil testes, isso é a diferença entre um build de 40 minutos e um de 4.

Vantagens e desvantagens

✅ Vantagens

  • Testável de verdade: núcleo testa com Java puro, rápido e sem infraestrutura.
  • Troca de peça sem cirurgia: mudar de Postgres pra Dynamo mexe num adapter, não no domínio.
  • Regra de negócio protegida: o código mais importante da empresa não depende de moda de framework.
  • Domínio rico: comportamento mora no modelo, não espalhado em services.

❌ Desvantagens

  • Mais código: ports, adapters, mapeamento domínio ↔ entidade. Um CRUD dobra de tamanho.
  • Curva de aprendizado: jr chega perdido — "por que tem três classes Produto??"
  • Overkill frequente: pra CRUD sem regra, é burocracia pura.
  • Disciplina constante: basta um dev com pressa importar JPA no domínio e a arquitetura furou.
Quando usar: sistemas com regra de negócio de verdade e vida longa — bancos, seguradoras, billing, motores de crédito. Times grandes onde o domínio precisa estar protegido de 30 devs mexendo ao mesmo tempo. Integrações que mudam (hoje REST, amanhã fila, depois gRPC) sobre o mesmo núcleo.

A história por trás dessas duas abas

Essas abas não saíram de livro — são literalmente as duas metades da minha carreira até aqui.

A primeira metade foi na TIVIT, a consultoria do meu primeiro emprego. Lá eu fazia projetos pequenos, pra clientes e internos, e o MVC era a escolha certa: entregas rápidas, baixa complexidade — sem motivo pra burocratizar o que era simples. Foi entregando assim que saí de estagiário pra fullstack pleno em pouco mais de 2 anos.

O hexagonal eu conhecia só de teoria — nunca tinha visto na prática até chegar no Banco Pan, onde estou hoje como arquiteto jr. Aqui o cenário inverte: projeto complexo, vida longa, e eu faço parte time de IDP (Internal Developer Platform) da empresa. Nesse contexto, desacoplar do framework deixa de ser preciosismo e vira necessidade.

Se a sua realidade hoje parece com a minha da TIVIT, abraça o MVC sem culpa. Se parece com a do Pan, o hexagonal vai fazer sentido rapidinho. As duas fases me construíram — e provavelmente vão construir você também.

$ git log --oneline minha-carreira

O veredito de quem viveu os dois

Não existe arquitetura vencedora — existe arquitetura adequada ao contexto. O MVC acoplado me ensinou a entregar; o hexagonal me ensinou a durar. Comece simples, e quando a regra de negócio ficar mais importante que a velocidade de entrega, você já sabe pra onde evoluir.
