Angular 21 limpo:
Signals, TypeScript estrito e PrimeNG 21 sem gambiarra

Pedro Neto • 25 set 2026 • 18 min de leitura

Front que “funciona” e vira inavegável em três sprints. Este post é o contrato de arquitetura que eu usaria num painel enterprise: standalone, Signals, tipagem que segura runtime e PrimeNG 21 por design tokens — com o Orders Desk como fio condutor.

⚡ signals + store → UI tipada sem ::ng-deep

O gap do pleno/sênior não é decorar o changelog do Angular 21. É montar um front module-less, com estado previsível, tipagem que reduz bug em produção e UI enterprise sem virar CSS spaghetti.

Vamos construir mentalmente o Orders Desk: painel B2B onde o operador filtra pedidos, abre detalhe e atualiza status. Uma feature. Várias decisões de arquitetura.

a ideia em uma frase Angular 21 moderno não é checklist de features — é contrato: uma fonte da verdade por concern, componentes burros que não buscam HTTP, e tema via tokens (não via ::ng-deep).
O que este post não é

Não é tutorial infinito de ng new nem tour pelo CLI. Assumo que você já levantou um projeto Angular. Aqui o foco é como encaixar as peças pra o código continuar legível daqui a seis meses. Signal Forms (experimental no 21) ficam só como nota de horizonte — o post precisa envelhecer bem.

O contrato Angular 21 (module-less de verdade)

Standalone deixou de ser “modo novo” e virou o caminho feliz. Feature module pra agrupar três componentes? Na maioria dos casos, ruído. Você importa o que o componente usa no próprio @Component({ imports: [...] }).

standalonemódulo some

Componente declara suas dependências. Sem NgModule de feature pra “organizar” o que a pasta já organiza.

@if / @for / @switchcontrol flow

Sintaxe nativa no template. @for exige track — e track por id, não por índice, se a lista muda.

providePrimeNGtema no app config

Tema e preset entram no bootstrap, igual HTTP e animações. Design system não é afterthought no styles.css.

Demo no blog

Aperte Demo nesse bloco (desktop ou celular): abre um modal com skeleton shimmer e, em seguida, a lista fake de pedidos. É HTML/CSS/JS — não é Angular rodando.

Trade-off: ainda dá pra usar *ngIf / *ngFor em código legado. Em feature nova Angular 21, control flow nativo. Menos diretiva importada, menos surpresa de change detection no template.

TypeScript como arquitetura (não ornamentação)

strict: true não é pedantismo. É freio de mão: o compilador pega o status inventado antes do cliente ligar reclamando.

order.model.ts — domínio explícito

export type OrderStatus =
  | 'PENDING'
  | 'PAID'
  | 'SHIPPED'
  | 'CANCELLED';

export interface Order {
  readonly id: string;
  readonly customerName: string;
  readonly totalCents: number;
  readonly createdAt: string; // ISO
  status: OrderStatus;
}

export interface OrderFilters {
  query: string;
  statuses: readonly OrderStatus[];
  from: Date | null;
  to: Date | null;
}

export type OrderListItem = Pick<Order, 'id' | 'customerName' | 'totalCents' | 'status' | 'createdAt'>;

export function isOrderStatus(value: string): value is OrderStatus {
  return (['PENDING', 'PAID', 'SHIPPED', 'CANCELLED'] as const).includes(
    value as OrderStatus,
  );
}

Utility types (Pick, Readonly) cortam boilerplate de DTO sem inventar interface gêmea. Generic no client HTTP protege o resto:

api-client.ts — generic enxuto

@Injectable({ providedIn: 'root' })
export class ApiClient {
  private readonly http = inject(HttpClient);

  get<T>(url: string, params?: Record<string, string>): Observable<T> {
    return this.http.get<T>(url, { params });
  }
}
O bug clássico da tabela any[]

Tipar p-table com any[] “pra ir mais rápido”. Seis meses depois alguém manda status: "paid" em minúsculo, o p-tag some o severity, e você descobre em produção. Type guard + union fecha a porta. Velocidade sem tipo é dívida com juros de UI mentindo.

Signals de ponta a ponta

No Orders Desk, o store é a fonte da verdade. Template só lê signal. Dumb components recebem input() e emitem output(). Sem async pipe no caminho feliz.

OrdersPage (smart) ├─ OrdersStore ← filters signal + httpResource ├─ OrderFiltersBar ← input filters / output filtersChange ├─ OrdersTable ← input orders + status / output select └─ OrderDetailDialog ← input order | null / output statusChange

orders.store.ts — uma fonte da verdade

@Injectable()
export class OrdersStore {
  private readonly http = inject(HttpClient);

  readonly filters = signal<OrderFilters>({
    query: '',
    statuses: [],
    from: null,
    to: null,
  });

  /** Página reseta quando o filtro muda — linkedSignal, não effect. */
  readonly page = linkedSignal({
    source: this.filters,
    computation: () => 0,
  });

  private readonly ordersResource = httpResource<OrderListItem[]>(() => {
    const f = this.filters();
    const page = this.page();
    return {
      url: '/api/orders',
      params: {
        q: f.query,
        status: f.statuses.join(','),
        page: String(page),
      },
    };
  });

  readonly status = computed(() => this.ordersResource.status());
  readonly orders = computed(() => this.ordersResource.value() ?? []);
  readonly error = computed(() => this.ordersResource.error());

  setFilters(next: OrderFilters): void {
    this.filters.set(next);
  }

  selectPage(page: number): void {
    this.page.set(page);
  }

  patchStatus(id: string, status: OrderStatus): void {
    // POST /api/orders/:id/status — no sucesso, recarrega a fonte
    this.http
      .post(`/api/orders/${id}/status`, { status })
      .subscribe({ next: () => this.ordersResource.reload() });
  }
}
effect só pra side-effect

Toast, analytics, foco no dialog — ok em effect. Sincronizar estado A → estado B com effect é cheiro de bug: use computed ou linkedSignal. Se você está “copiando” um signal pro outro, pare e redesenhe a fonte da verdade.

computed = derivação só leitura. linkedSignal = estado gravável que reage a outra fonte (página zera quando filtro muda). Escolher errado aqui é o equivalente front do “Subject pra tudo”.

Smart vs Dumb com PrimeNG 21

Regra dura: dumb não injeta HttpClient. Dumb não conhece URL. Dumb recebe dados e grita eventos. O container (OrdersPage) fala com o store.

orders-page.ts — smart container

@Component({
  selector: 'app-orders-page',
  imports: [
    OrderFiltersBar,
    OrdersTable,
    OrderDetailDialog,
    Toast,
  ],
  providers: [OrdersStore],
  template: `
    <p-toast />
    <app-order-filters-bar
      [filters]="store.filters()"
      (filtersChange)="store.setFilters($event)"
    />
    <app-orders-table
      [orders]="store.orders()"
      [status]="store.status()"
      (selectOrder)="selected.set($event)"
    />
    <app-order-detail-dialog
      [order]="selected()"
      (closed)="selected.set(null)"
      (statusChange)="onStatus($event)"
    />
  `,
})
export class OrdersPage {
  readonly store = inject(OrdersStore);
  readonly selected = signal<OrderListItem | null>(null);
  private readonly messages = inject(MessageService);

  onStatus(e: { id: string; status: OrderStatus }): void {
    this.store.patchStatus(e.id, e.status);
    this.messages.add({
      severity: 'success',
      summary: 'Status atualizado',
      detail: e.id,
    });
  }
}

order-filters-bar.ts — dumb + PrimeNG

@Component({
  selector: 'app-order-filters-bar',
  imports: [FormsModule, InputText, MultiSelect, DatePicker, Button],
  template: `
    <label for="q">Busca</label>
    <input
      id="q"
      pInputText
      [ngModel]="draft().query"
      (ngModelChange)="patch({ query: $event })"
    />

    <p-multiselect
      inputId="status"
      [options]="statusOptions"
      [ngModel]="draft().statuses"
      (ngModelChange)="patch({ statuses: $event })"
      placeholder="Status"
    />

    <p-datepicker
      selectionMode="range"
      [ngModel]="range()"
      (ngModelChange)="onRange($event)"
    />

    <p-button label="Filtrar" (onClick)="apply()" />
  `,
})
export class OrderFiltersBar {
  readonly filters = input.required<OrderFilters>();
  readonly filtersChange = output<OrderFilters>();

  readonly draft = signal<OrderFilters>({
    query: '',
    statuses: [],
    from: null,
    to: null,
  });

  readonly statusOptions = [
    { label: 'Pendente', value: 'PENDING' },
    { label: 'Pago', value: 'PAID' },
    { label: 'Enviado', value: 'SHIPPED' },
    { label: 'Cancelado', value: 'CANCELLED' },
  ];

  constructor() {
    effect(() => this.draft.set(this.filters()));
  }

  readonly range = computed(() => {
    const f = this.draft();
    return f.from && f.to ? [f.from, f.to] : null;
  });

  patch(partial: Partial<OrderFilters>): void {
    this.draft.update((d) => ({ ...d, ...partial }));
  }

  onRange(value: Date[] | null): void {
    this.patch({
      from: value?.[0] ?? null,
      to: value?.[1] ?? null,
    });
  }

  apply(): void {
    this.filtersChange.emit(this.draft());
  }
}

PrimeNG no Orders Desk (mapa rápido):

  • p-table — lista com sort; loading/empty via @if + status do resource
  • p-multiselect / p-datepicker — filtros
  • p-tag — severity por OrderStatus (union tipada)
  • p-skeleton — loading sem spinner solto no meio da tela
  • p-dialog — detalhe (dumb)
  • p-toast + MessageService — feedback da ação

Proibido no exemplo: ::ng-deep pra “ajustar rapidinho” o PrimeNG. Se a cor está errada, mexa no preset / token do componente. Override de classe é último recurso — e quando entra, documenta o porquê.

Acessibilidade e tema sem gambiarra

PrimeNG mira WCAG AA. Isso não te salva se o preset matar o focus ring ou o contraste cair no dark mode.

  • darkModeSelector: '.app-dark' — você controla o toggle; tokens light/dark vêm do preset
  • Todo input com label + inputId / for
  • Dialog fecha com Esc; foco volta pro trigger
  • Tabela: linha clicável também acionável por teclado (botão “ver” na célula, não só click na tr)
Bonito no Figma, ilegível no Tab

Customizei primary, removi outline “porque feio”, shippei. QA de acessibilidade: impossível navegar a tabela. Focus ring é feature, não bug visual. Se o design odeia o ring padrão, troque o token de focus — não delete a indicação.

O erro real (e a regra pra levar)

Eu já misturei BehaviorSubject no service, signal no componente e um pedaço de estado só no template (“variável local pra o dialog”). Resultado: filtro atualizava a lista, o dialog ainda mostrava o pedido antigo, toast disparava duas vezes. A UI mentia.

Não foi falta de PrimeNG. Foi falta de dono do estado.

✔ Uma fonte por concern

  • Filtros → OrdersStore.filters
  • Lista async → httpResource
  • Seleção de UI → signal no page
  • Dumb só lê/emite

✖ O atalho que dói

  • Subject + signal “pro mesmo dado”
  • HTTP no componente da tabela
  • any[] no p-table
  • ::ng-deep pra tema
Horizonte Angular 21: Signal Forms existem e são promissoras, mas ainda experimentais. Neste post os filtros usam signal state + PrimeNG de propósito — API estável, mesmo modelo mental do resto do desk. Quando Signal Forms estabilizar, o store continua; só a forma de editar o draft muda.

Por que o front entra na leva 3 agora

Leva 1 e 2 foram alicerce backend e vocabulário (Java, DDD, SOLID, dicionários). Leva 3 abre o front de verdade: o mesmo rigor de arquitetura, do outro lado do HTTP.

Orders Desk é o tipo de tela que aparece em banco, varejo, ops — não um to-do. Se você segura Signals + tipagem + PrimeNG sem gambiarra aqui, o portfólio depois (post 15) para de ser “telinha bonita” e vira evidência de decisão.

O resumo pra levar pra casa

Uma fonte da verdade por concern. Store com Signals e httpResource; dumb não busca HTTP; TypeScript estrito na borda do PrimeNG; tema por tokens. Angular 21 limpo não é moda — é o freio de mão pra o front não virar vibecoding com CSS.
