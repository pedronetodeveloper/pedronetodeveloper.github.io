Fundação em Cloud:
AWS e Azure pra quem está começando

Pedro Neto • 15 jul 2026 • 16 min de leitura

Os serviços que todo estagiário e jr vai esbarrar no primeiro emprego, explicados sem sopa de letrinhas. E um aviso importante: as abas aqui não competem — AWS e Azure resolvem os mesmos problemas com nomes diferentes. Aprendeu o conceito numa, você já sabe na outra.

☁️ AWS ≈ 🔷 Azure
☁️ Antes de tudo: o que é "nuvem"? ▼

É alugar infraestrutura de outra empresa em vez de comprar a sua: servidor, armazenamento, rede — tudo sob demanda, pagando pelo que usar, sem se preocupar com a máquina física.

O pulo do gato pra quem está começando: os serviços são conceitos, não marcas. "Guardar arquivo", "rodar máquina", "distribuir tráfego", "controlar permissão" — todo provedor tem uma resposta pra cada um. Este post apresenta as respostas da AWS e da Azure, lado a lado.

como pensar a aws "Cada serviço faz UMA coisa bem feita. Sua aplicação é a soma de blocos pequenos — e o segredo é saber qual bloco resolve qual problema."

A AWS é a nuvem com maior fatia de mercado, e é a que mais aparece em vaga de jr. A boa notícia: das centenas de serviços do catálogo, você precisa conhecer bem menos de dez pra se virar. São esses aqui:

internet │ 🛡️ WAF (filtra ataque) │ 🚪 API Gateway ─── ⚖️ Load Balancer │ │ ⚡ Lambda 🖥️ EC2 (com imagem do 📦 ECR) │ │ └──── 🗄️ S3 ───────┘ │ 🔑 IAM controla quem acessa o quê

🗄️ Guardar e rodar: S3, EC2 e ECR

🗄️ S3 Simple Storage Service

O baú de arquivos da nuvem: guarda qualquer coisa (PDF, imagem, backup, log) em "buckets", com durabilidade altíssima e pagando centavos por GB.

Você vai usar quando: a aplicação precisar guardar upload de usuário — tipo os currículos do sistema de RH do post anterior.

🖥️ EC2 Elastic Compute Cloud

A máquina virtual clássica: você escolhe CPU, memória e sistema, e ganha um servidor que fica de pé o tempo que você quiser — pagando por hora ligada.

Você vai usar quando: a aplicação precisa estar sempre rodando, como uma API Spring Boot que não pode ter cold start.

📦 ECR Elastic Container Registry

A prateleira das suas imagens Docker: o pipeline builda a imagem, empurra pro ECR, e de lá ela é puxada pra rodar onde precisar.

Você vai usar quando: o time trabalha com containers (spoiler: quase todo time hoje trabalha).

O erro mais famoso da AWS inteira: bucket S3 público sem querer. Vazamento de dado atrás de vazamento de dado começou assim. Regra de ouro: bucket nasce privado e SÓ vira público com justificativa por escrito — de preferência com alguém sênior assinando junto.

🚦 Distribuir e proteger: Load Balancer, API Gateway e WAF

⚖️ Load Balancer ELB / ALB

O porteiro que distribui: recebe o tráfego e reparte entre suas instâncias, tirando da roda quem está doente (health check) e mantendo a app de pé se uma máquina cair.

Você vai usar quando: tiver mais de uma instância da mesma aplicação — ou seja, em qualquer sistema sério.

🚪 API Gateway Amazon API Gateway

A recepção da sua API: expõe rotas HTTP, valida autenticação, limita requisições por cliente (rate limit) e encaminha pro backend — Lambda, EC2, o que for.

Você vai usar quando: quiser expor Lambdas como API REST sem gerenciar servidor — o par perfeito do serverless.

🛡️ WAF Web Application Firewall

O segurança da porta: inspeciona as requisições antes de chegarem na aplicação e barra os golpes conhecidos — SQL injection, XSS, bots maliciosos.

Você vai usar quando: a API é pública e você não quer descobrir o que é SQL injection da pior forma possível.

⚡ Serverless e permissões: Lambda e IAM

⚡ Lambda AWS Lambda

Código sem servidor: você sobe a função, a AWS executa quando o evento chega e cobra por execução. Parado? Custo zero. (Você já viu ela em ação no post de Python & IaC.)

Você vai usar quando: a tarefa é "recebe, processa, responde" — API pequena, processamento de upload, automação agendada.

🔑 IAM Identity and Access Management

O serviço mais importante da lista — e o menos glamouroso. Controla quem (usuário, aplicação, serviço) pode fazer o quê em qual recurso. Usuários, roles e policies.

Você vai usar quando: sempre. Literalmente tudo na AWS passa pelo IAM. Aprenda o princípio do menor privilégio: cada um só acessa o que precisa.

O erro que assombra todo jr: access key do IAM commitada no GitHub. Bot varre repositório público 24/7 procurando isso — em minutos sua conta vira fazenda de mineração de cripto e a fatura explode. Credencial NUNCA vai pro código: use variável de ambiente, secrets manager ou role.
Por onde começar na AWS: conta gratuita (free tier), um bucket S3 pra entender storage, uma Lambda pra sentir o serverless, e o IAM desde o dia um — usuário próprio, sem usar a conta root. Esses três + a certificação CLF-C02 te dão a base que o mercado pede de um jr.
como pensar a azure "Mesmos blocos, outros nomes — com integração forte no mundo Microsoft. Se sua empresa vive de Office, Teams e Active Directory, é bem provável que a nuvem dela seja essa."

A Azure é a segunda maior nuvem do mundo e domina em empresa grande e banco — foi nela que eu comecei, no estágio. E aqui vai a mágica deste post: cada serviço abaixo é o equivalente direto de um que você viu na aba AWS. O conceito você já sabe; só muda o crachá.

internet │ 🛡️ WAF (no Application Gateway / Front Door) │ 🚪 API Management ─── ⚖️ Load Balancer / App Gateway │ │ ⚡ Azure Functions 🖥️ Virtual Machines (com imagem do 📦 ACR) │ │ └──── 🗄️ Blob Storage ┘ │ 🔑 Entra ID + RBAC controla quem acessa o quê

🗄️ Guardar e rodar: Blob Storage, VMs e ACR

🗄️ Blob Storage ≈ S3 na AWS

O baú de arquivos da Azure: "blobs" dentro de containers, dentro de uma Storage Account. Mesma ideia do S3 — arquivo de qualquer tipo, durável, barato.

Você vai usar quando: guardar uploads, backups e estáticos. Foi onde os currículos do meu projeto de estágio iam parar.

🖥️ Virtual Machines ≈ EC2 na AWS

A máquina virtual da Azure: mesma proposta do EC2 — você escolhe o tamanho, o sistema, e paga pelo tempo ligada.

Você vai usar quando: precisar de um servidor sempre de pé, com controle total do ambiente.

📦 ACR Azure Container Registry ≈ ECR

A prateleira de imagens Docker da Azure. O fluxo é idêntico: pipeline builda, empurra pro ACR, e o runtime puxa de lá.

Você vai usar quando: o time containeriza as aplicações — e a esteira (Azure Pipelines!) cuida do push.

🚦 Distribuir e proteger: Load Balancer, API Management e WAF

⚖️ Load Balancer / Application Gateway ≈ ELB / ALB

Dois nomes pra mesma missão de distribuir tráfego: o Load Balancer trabalha na camada de rede, e o Application Gateway entende HTTP (rotas, certificado, cookie) — como o ALB da AWS.

Você vai usar quando: tiver múltiplas instâncias — e o Application Gateway quando precisar de decisões por URL.

🚪 API Management ≈ API Gateway na AWS

A recepção das suas APIs na Azure: publica rotas, exige autenticação, aplica rate limit e ainda gera um portal de documentação pros consumidores.

Você vai usar quando: expor APIs (inclusive Azure Functions) de forma controlada pra outros times ou clientes.

🛡️ WAF módulo do App Gateway / Front Door

Na Azure, o firewall de aplicação vem como recurso do Application Gateway ou do Front Door — mesma missão: barrar SQL injection, XSS e bots antes de chegarem na sua aplicação.

Você vai usar quando: a aplicação é pública. Mesma regra da AWS: melhor ter e não precisar.

⚡ Serverless e permissões: Functions e Entra ID

⚡ Azure Functions ≈ Lambda na AWS

O serverless da Azure — e o serviço onde nasceu minha primeira aplicação profissional. Função que executa por evento, cobra por execução, dorme de graça.

Você vai usar quando: "recebe, processa, responde" — igualzinho à Lambda. O projeto de currículos do RH rodava exatamente aqui.

🔑 Microsoft Entra ID + RBAC ≈ IAM na AWS

O controle de identidade e acesso da Azure: o Entra ID (ex-Active Directory) gerencia quem existe, e o RBAC define o que cada um pode fazer em cada recurso. Managed Identities dão identidade às aplicações sem senha no código.

Você vai usar quando: sempre — igual ao IAM. E o princípio é o mesmo: menor privilégio, desde o primeiro dia.

Percebeu o padrão? Você acabou de "aprender" oito serviços da Azure em cinco minutos — porque já tinha aprendido os conceitos na aba AWS. É assim que cloud funciona: domine os conceitos uma vez e todo provedor vira sotaque.
Por onde começar na Azure: conta gratuita, uma Function pra sentir o serverless (é onde eu comecei!), um Blob Storage pra entender storage, e o portal do Entra ID pra visualizar identidade e acesso. Se sua empresa é mundo Microsoft, esse caminho te deixa produtivo rápido.

A história por trás desse post

Minha ordem foi invertida em relação à maioria: comecei pela Azure, no estágio — Azure Functions rodando o sistema de currículos, deploy por esteira no Azure Pipelines. A nuvem nunca foi teoria pra mim; foi o palco do meu primeiro projeto.

A AWS veio depois, pelos estudos: tirei a AWS Certified Cloud Practitioner (CLF-C02) e hoje mantenho projetos com Lambda e serverless no meu GitHub. E foi estudando as duas que a ficha caiu: eu não estava aprendendo "outra nuvem" — estava revendo os mesmos conceitos com nomes novos.

É por isso que este post não elege vencedor. As duas me empregaram, as duas me ensinaram, e conhecer as duas me deixou mais completo. A escolha, na prática, quase nunca é sua — é da empresa. Sua vantagem é transitar bem em qualquer uma.

O veredito de quem transita nas duas

Nuvem se aprende por conceito, não por marca. Guardar arquivo, rodar máquina, distribuir tráfego, executar função, controlar acesso — domine essas cinco ideias e você se vira na AWS, na Azure e na próxima nuvem que inventarem.
